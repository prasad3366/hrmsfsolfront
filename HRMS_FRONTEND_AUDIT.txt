HRMS Frontend Read-Only Architecture and Behavior Audit

This audit is based on the current implementation in src/App.tsx, src/context/AuthContext.tsx, src/services/api.ts, and the feature modules under src/modules.

1) Architecture: actual data flow

Route → Page → Component → Auth → ApiService → Backend

- Route protection and role gating live in src/App.tsx.
  - ProtectedRoute waits on isLoading, redirects unauthenticated users to /login, and blocks pages when allowedRoles does not include the user role.
  - /login redirects authenticated users to /dashboard.
  - Most feature routes are nested under the main layout in src/components/layout/Layout.tsx.

- Layout shell is in src/components/layout/Layout.tsx.
  - It renders the sidebar and topbar, then the current route view in <Outlet />.

- Sidebar navigation and role-specific menu visibility are in src/components/layout/Sidebar.tsx.
  - ADMIN/HR get employee, attendance, recruitment, assets, reports, settings.
  - MANAGER gets employees, employee attendance, performance, and fewer HR/admin entries.
  - EMPLOYEE gets common modules plus performance.

- Authentication state is centralized in src/context/AuthContext.tsx.
  - initializeAuth reads accessToken and foodeez_user from localStorage.
  - It decodes JWT claims, builds a user object by email, role, name, and employeeId.
  - On load it tries api.getEmployeeIdByUserId() to resolve employee linkage.
  - login calls api.login, decodes the returned access token, stores the user and tokens, then refreshes employeeId.

- Shared API logic is in src/services/api.ts.
  - This file is a singleton ApiService and wraps global fetch with a refresh-on-401 mechanism.
  - Headers are built with getAuthHeaders(), which includes Authorization: Bearer <accessToken> and Content-Type: application/json.
  - A global fetch override replays failed requests after token refresh.
  - This affects every feature, including document uploads.

- Notification and temporary local persistence are supported in src/context/NotificationContext.tsx and in some modules via localStorage fallback, especially helpdesk tickets.

2) Feature-by-feature audit

A. Login
Files:
- src/components/auth/Login.tsx
- src/context/AuthContext.tsx

1. UI behavior
- Shows email/password form with password visibility toggle and Forgot password modal.
- Submits login via handleSubmit and navigates to /dashboard on success.
- Displays inline validation and login failure messaging.

2. API calls
- AuthContext.login(...) → api.login(email, password)
- POST call to ${API_BASE_URL}/auth/login in src/services/api.ts.

3. State management
- Local component state for email, password, showPassword, error, loading, isForgotPasswordOpen, successMessage.
- AuthContext stores user, role, isLoading.

4. Authentication handling
- Stores accessToken and refreshToken in localStorage.
- Decodes JWT payload to build user.
- Redirects to /dashboard when authenticated.

5. Role-based access
- Role is derived from JWT claims and stored in user.role.
- App routes then determine page access.

6. Error handling
- Empty field validation in the form.
- API failure surfaces result.message.
- Catch block converts errors to user-visible messages.

7. Loading states
- loading state disables submit and shows UI text.
- App-level isLoading during auth bootstrap.

8. Fallback logic
- If JWT decode fails, it falls back to email-based user creation.
- If foodeez_user is present, it can bootstrap from localStorage.

9. Data mapping
- buildUserFromJwt maps JWT claims to the app user object.
- employeeId is derived from jwt.employeeId when present.

10. Dependencies on other features
- Login creates the app-wide auth state used by all pages.
- Layout, Sidebar, and route guard rely on that state.

11. Current problems
- Remember me is visual-only and does not affect auth behavior.
- There is an artificial 100ms UI delay before login.
- The app assumes role information is always present in the token; otherwise fallback is partial.

12. Must be preserved
- Auth redirects to dashboard on valid login.
- Tokens are persisted and reused across the session.
- Route guard continues to block unauthorized pages.

4) Shared request/response layer and auth behavior

This is the most important shared system-level fact:

- All API requests in src/services/api.ts pass through a custom global fetch override.
- The refresh flow is centralized here:
  - If a response status is 401, it tries POST /auth/refresh with refreshToken.
  - If refresh succeeds, it retries the original request.
  - It reuses withFreshAuthHeaders to add updated auth headers.

This means:
- The refresh wrapper is global and affects every feature, not just auth.
- Any request mutated or rebuilt incorrectly inside this layer can break unrelated features.
- Multipart requests are especially sensitive because the wrapper creates JSON headers for the retried request and may override multipart boundaries unless the request is treated specially.

5) Current problems visible across the frontend

Across the app, the current frontend behavior shows several recurring realities:

- The app frequently falls back to localStorage or best-effort normalization rather than strict backend contract validation.
- Some modules silently swallow backend failures and continue with empty arrays.
- Several pages assume nested backend shapes like user.email, employee.user.role, employee.leaves, salaries[0] and normalize around those assumptions.
- Route-level permission enforcement exists, but not every page enforces finer-grained UI controls.
- The app has a broad multi-fallback API strategy, which makes it resilient but also makes root-cause analysis harder when a failure is not clearly owned by one endpoint.

6) What must be preserved by design

The current frontend is intentionally shaped around these behaviors and should remain stable unless the product explicitly changes them:

- Authenticated bootstrap from JWT + localStorage.
- Route-based role gating.
- Separate employee, manager, and HR/admin views.
- Global token refresh and retry across all API calls.
- Multi-endpoint fallback logic for employee lookup and several data models.
- LocalStorage fallback behavior in helpdesk and user bootstrapping.
- Feature-local loading/error states and alert banners.
- Current dashboard role switch and page navigation flow.

This audit establishes the actual implementation behavior without modifying any code.
