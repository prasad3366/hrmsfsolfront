4. Exact current frontend expectation for assignment/reassignment
------------------------------------------------------------------

The current frontend expects an asset assignment to be initiated with:

POST /api/assets/assign

{
  "assetId": <asset id>,
  "employeeId": <employee id>
}

The assignment UI is a modal titled Assign Asset. It selects an active
employee and submits the selected employee's numeric ID as employeeId.

There is no separate reassignment contract. There is no reassignment endpoint,
no reassignment request body, and no assignment-history UI in the executable
frontend.

5. Current support for asset operations
---------------------------------------

Assigning an unassigned asset:

SUPPORTED.

Assets.tsx renders Assign when:

asset.status !== 'RETURNED' && !asset.assignedTo

The modal then submits assetId and employeeId to POST /assets/assign.

Reassigning an assigned asset:

NOT SUPPORTED by the current executable frontend.

When an asset has assignedTo, the page does not show Assign or Reassign. It
shows only Return. There is no UI for selecting a replacement employee while
the asset remains assigned.

Returning an asset:

SUPPORTED.

Assets.tsx renders Return when:

asset.status !== 'RETURNED' && asset.assignedTo

The frontend sends PUT /assets/return/{assetId} with no request body.

After either assignment or return, useAssets() refreshes the asset list.

7. Compatibility issues with AVAILABLE status
----------------------------------------------

The frontend Asset type in src/services/api.ts currently declares:

status: 'ASSIGNED' | 'RETURNED';

Adding AVAILABLE as a backend status creates a TypeScript type mismatch until
the frontend type is updated.

At runtime, Assets.tsx has a fallback status badge labeled Unassigned. An
AVAILABLE asset with no assignedTo would therefore likely display as Unassigned
and meet the existing Assign-button condition. However, AVAILABLE is not part
of the declared frontend status union.

The current UI also treats RETURNED as terminal:

- RETURNED assets do not show Assign.
- RETURNED assets do not show Return.

Therefore, if A-5 uses AVAILABLE to represent a reusable unassigned asset,
the backend must preserve response fields and assignment behavior expected by
the existing frontend, or the frontend type and terminal-status logic must be
updated in a later coordinated change.

8. Compatibility issues with reassignment history
--------------------------------------------------

The current frontend supports only the current assignment fields:

- assignedTo
- assignedAt
- returnedAt
- status

It does not consume assignment-history records and has no history endpoint or
history display.

A backend reassignment-history implementation can be added without breaking
the current frontend if:

- POST /assets/assign remains available with assetId and employeeId.
- The current asset response fields remain compatible.
- Existing return behavior remains available.
- Additional history data is additive rather than replacing current fields.

The current frontend will ignore any new history data and will continue to
require the current asset to be returned before another assignment can be
started through the UI.

Final determination
-------------------

An executable frontend contract DOES exist.

The contract is:

POST /api/assets/assign
Body: { assetId: number, employeeId: number }

The frontend supports assigning an unassigned asset and returning an assigned
asset. It does not support reassigning an assigned asset. A-5 should preserve
the assignment endpoint and body, and should treat AVAILABLE and assignment
history as additive backend changes unless a coordinated frontend contract
change is intentionally introduced.
